1. Architecture principles
1. Own the experience, rent operations (D-001). TAB owns the website, the client
relationship model, plans, programs, and progress. Scheduling (Timely) and payments
(Stripe) stay with specialist systems.
2. One application, two audiences. A single Next.js app serves the public site, the My
TAB client portal, and the practitioner workspace.
3. Sensitive by design (D-042). The client domain is treated as a health-data system:
RLS, audit, MFA, BAAs. Nothing sensitive leaks into analytics, logs, URLs, email
subjects, or notifications.
4. Model for a team, build for one (D-045). Roles and care-team assignment are data;
the MVP ships owner-practitioner and client only.
5. Configuration over code. Business-editable values live in config/; content lives in
Payload-shaped files until the CMS is wired.
6. Managed infrastructure (Step 16.6). Open source does not mean self-hosted. No self-
hosting without a stated reason.
7. Supported interfaces only. No scraping, no unsupported two-way sync. Timely has no
public API (D-003), so we link out.

5. Integration patterns
Timely (D-003). Booking and client-login URLs come from config/site.ts, with optional
per-service deep links. If unset, CTAs fall back to /book, which offers email scheduling. No
data sync at launch. When Timely Innovate is adopted (D-015), use the documented Zapier
feed for next-appointment summaries only.
Stripe (D-004, D-052). Timely owns appointment and package payments. Stripe direct
owns digital products and coaching subscriptions. Built: openBillingPortal() creates a
Customer Portal session for the signed-in client. To build: Checkout for sellable programs
(D-044), and a webhook route (/api/stripe/webhook, signature-verified) that creates
enrollments on purchase and updates membership status. Store only IDs and status.
Resend. lib/email.ts sends plain-text notifications to info@tabwellnesscollective.com.
Subjects never carry personal or health details. Without RESEND_API_KEY it logs to the
server console. Sender domain must be verified.
Plausible and Meta (D-046). Loaded by components/Analytics.tsx only when
configured, and never on /my-tab, /practice, /start, or /contact. No custom events
carry form content.
Legacy redirects (D-040). config/redirects.ts maps 64 crawled tabmassage.com
URLs plus prefix rules. Middleware issues single-hop 308s; requests on the
tabmassage.com host land on the canonical www.tabwellnesscollective.com.
Payload (D-036, future). Content files map 1:1 to collections: services, pages (globals),
faqs, team, resources, programTemplates. Payload runs inside the same Next.js app on
the same Postgres instance under a separate schema, or its own database; decide under A-
02.

Authorization model. RLS on every table, using security definer helpers with a fixed
search_path: current_client_id(), current_practitioner_id(), is_owner(),
can_access_client(uuid). Clients read their own rows, and only shared rows where
sharing applies. Practitioners reach clients through primary assignment or care_team.
Owner access is universal but audited. Staff-only routes also check
current_practitioner_id() in the app layer.
Audit. Triggers write insert, update, and delete events on sensitive tables to audit_log.
Reads are not audited at the database level (see A-05).
Data access in the app. Screens call only lib/portal/repo.ts, which switches between
demo data and supabase-repo.ts via siteConfig.portal.dataSource. Queries run as the
signed-in user; the service-role key is never used for client-facing reads.
